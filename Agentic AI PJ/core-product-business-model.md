# 業務知識グラフ型 AI オペレーション基盤: コアプロダクト整理

作成日: 2026-05-03

## 1. 位置づけ

本プロダクトは、企業内の会話、文書、業務イベント、システム更新、顧客対応ログを継続的に構造化し、企業ごとの業務知識グラフを育てながら、AI エージェントが回答、提案、業務実行、改善を行うための基盤である。

単なるチャットボットや社内検索ではなく、以下を同時に提供する。

- 企業固有の業務メモリ
- 根拠付き回答
- 既存業務システムへの安全なアクション
- 承認、監査、評価、改善ループ
- 成果に基づく業務価値の可視化

一言で表すと、**企業が AI を使うほど、業務知識、顧客理解、対応品質、実行精度が蓄積される AI オペレーション基盤**である。

## 2. 中心仮説

企業が AI を利用すると、毎回以下のようなデータが発生する。

- ユーザーの質問
- AI の回答
- 参照された文書
- 利用された社内データ
- 実行されたツール
- 承認、却下、修正
- 業務上の最終結果
- 再質問、エスカレーション、失敗

通常の AI ツールでは、これらはログとして残るだけで、次の業務に再利用されにくい。

本プロダクトでは、これらをイベントとして保存し、人物、顧客、組織、案件、論点、制約、意思決定、成果などのノードと関係性に変換する。これにより、企業ごとの知識グラフが継続的に成長する。

その結果、AI は毎回ゼロから大量の文書を読むのではなく、根拠、関係性、過去判断、信頼度を持つ構造化メモリを参照できる。

## 3. 解く課題

### 3.1 企業知識が散らばっている

多くの企業では、重要な情報が以下に分散している。

- FAQ
- SOP
- CRM
- チケット管理
- メール
- Slack や Teams
- 議事録
- 商談メモ
- 請求書
- 契約書
- 社内 Wiki
- BI / DWH
- 担当者の記憶

これらは検索可能であっても、関係性として整理されていないことが多い。

### 3.2 AI の回答が根拠や文脈を欠きやすい

汎用 AI は、似た文書を探して回答することはできる。しかし、企業固有の業務では以下が重要になる。

- この顧客には過去に何が起きたか
- どの契約条件が有効か
- 誰が承認権限を持つか
- どの判断が最新か
- どの情報は推測で、どの情報は事実か
- どの業務処理には人間承認が必要か

単純なベクトル検索だけでは、これらの関係性と信頼度を十分に扱えない。

### 3.3 AI 導入の効果が一過性になりやすい

チャット UI を導入しても、利用ログが次の改善に繋がらなければ、効果は限定的になる。

本来は、AI が失敗した会話、ユーザーが修正した回答、解決に至った対応、成果に繋がった提案をすべて学習材料として扱うべきである。

ただし、基盤モデルを即座に再学習する必要はない。まず改善すべきなのは、検索、ランキング、抽出ルール、信頼度補正、顧客別の好み、曖昧さ検知である。

## 4. 提供価値

### 4.1 回答する

企業の文書、会話履歴、CRM、チケット、業務データをもとに、根拠付きで回答する。

重要なのは、回答文だけではなく、以下を合わせて返すことである。

- 参照した根拠
- 根拠の種類
- 情報の新しさ
- 信頼度
- 競合する情報
- 人間確認が必要な箇所

### 4.2 実行する

AI は単なる案内ではなく、既存システムに対して業務アクションを行う。

例:

- CRM 更新
- チケット作成
- 承認依頼
- 顧客への返信案作成
- 請求情報の確認
- 予約変更
- 契約レビュー依頼
- 社内担当者へのエスカレーション
- レポート生成

ただし、書き込み系、金銭系、契約系、個人情報系のアクションは、権限、ルール、承認、監査ログで制御する。

### 4.3 覚える

AI の利用ログをそのまま保存するのではなく、業務上意味のある構造に変換する。

例:

- 顧客 A は価格より納期を重視する
- 案件 B は法務確認が未完了
- 契約 C は自動更新条項がある
- 担当者 D は支払い条件の承認者である
- 問い合わせ E は過去の障害 F と類似している
- 提案 G は却下され、理由は予算不足だった

このような関係性を、根拠と信頼度付きで保存する。

### 4.4 改善する

利用結果を改善ループに戻す。

改善対象は以下である。

- 検索対象の選び方
- サブグラフのランキング
- 回答候補のランキング
- 情報抽出プロンプト
- 関係タイプ分類
- 信頼度補正
- 顧客別の好み
- 曖昧な関係の検出
- エスカレーション条件

これにより、利用量が増えるほど、企業ごとの AI 品質が改善される。

### 4.5 統制する

企業利用では、AI の自由度よりも統制が重要になる場面が多い。

本プロダクトでは以下を標準機能とする。

- 権限管理
- 承認ワークフロー
- 監査ログ
- 参照根拠の保存
- 出力監査
- ツール実行ログ
- データ保持ポリシー
- テナント分離
- 機密情報マスキング
- 変更履歴
- シミュレーションと回帰テスト

## 5. 対象顧客

### 5.1 初期ターゲット

初期顧客は、以下の特徴を持つ企業が望ましい。

- 問い合わせ、商談、契約、運用の情報が複雑
- 人間の判断や承認が完全には外せない
- 既存システムが複数存在する
- 業務ログが多いが、活用されていない
- AI の回答品質だけでなく、業務成果を重視する
- 監査、説明責任、権限管理が必要

具体的には以下の領域が候補になる。

- B2B SaaS のカスタマーサクセス
- 金融、保険、不動産の顧客対応
- 医療、介護、ヘルスケアの業務支援
- 製造業の保守、部品、品質対応
- 法務、会計、コンサルティング
- 大企業の社内業務支援

### 5.2 避けるべき初期領域

初期段階では、以下は避ける方がよい。

- 完全自動化が前提の高頻度取引
- 人命に直接関わるリアルタイム判断
- 法規制上、説明責任を満たしにくい領域
- データ連携が極端に困難な企業
- AI 導入目的が曖昧な企業
- 価格だけで選ぶ小規模セルフサーブ市場

## 6. プロダクト構成

### 6.1 Agent Workspace

業務担当者が AI と対話しながら、回答、調査、文書作成、業務実行を行う画面。

主な機能:

- チャット
- 根拠付き回答
- 参照ノード表示
- ツール実行
- 承認依頼
- 修正フィードバック
- 過去会話検索
- タスク化

### 6.2 Knowledge Ingestion

文書、会話、システムイベントを取り込む層。

対象データ:

- PDF
- Markdown
- Office 文書
- CRM レコード
- チケット
- メール
- チャット
- 議事録
- 音声文字起こし
- API イベント
- BI / DWH テーブル

### 6.3 Private Knowledge Graph

企業ごとに分離された知識グラフ。

主なノード:

- Customer
- Person
- Company
- Project
- Issue
- Requirement
- Decision
- Preference
- Document
- Conversation
- Action
- Outcome
- Contract
- Ticket
- Meeting

主なエッジ:

- mentions
- owns
- requested_by
- approved
- rejected
- depends_on
- blocked_by
- caused_by
- contradicts
- similar_to
- evidence_for
- resolved_by
- follow_up_for

### 6.4 Review Console

AI が抽出したノード、エッジ、事実候補を確認する管理画面。

信頼度は以下のように扱う。

- `EXTRACTED`: ソースに明示された情報
- `INFERRED`: モデルが妥当に推論した情報
- `AMBIGUOUS`: 不確実でレビューが必要な情報

重要なルール:

- 推論は事実として扱わない
- すべての関係に根拠を持たせる
- 高リスク情報は承認必須にする
- 古い情報は削除ではなく失効として扱う
- 矛盾は上書きせず、矛盾関係として保存する

### 6.5 Workflow Builder

業務フローを定義する機能。

例:

- 問い合わせ受付
- 顧客確認
- 文書検索
- 回答生成

- ツール実行
- 結果確認
- エスカレーション
- ログ保存
- 改善候補作成

### 6.6 Tool Integration

既存システムへの接続。

接続対象:

- CRM

- 決済
- 予約

本番投入前に、業務シナリオを使ってエージェントを検証する。

検証項目:

- 正答率
- 根拠一致率
- 承認判断

表示するもの:

## 7. 主要ユースケース

### 7.1 カスタマーサクセス

顧客ごとの契約、利用状況、問い合わせ、過去要望、解約兆候を統合し、担当者の対応を支援する。

成果:

- 回答時間短縮
- 解約リスク検知
- アップセル候補発見
- 引き継ぎ品質向上
- 顧客文脈の保持

### 7.2 社内業務支援

社員が社内規程、申請手順、過去判断、担当部署を検索し、必要な申請や承認まで進められる。

成果:

- 問い合わせ削減
- 業務手順の標準化
- 属人化解消
- 承認フロー短縮

### 7.3 営業支援

商談履歴、顧客課題、競合、決裁者、過去提案、社内類似案件をもとに、次の提案やリスクを提示する。

成果:

- 商談準備時間短縮
- 提案品質向上
- 類似成功事例の再利用
- 失注理由の構造化

### 7.4 専門業務支援

法務、会計、医療、金融など、根拠と承認が重要な業務で、調査、文書作成、レビュー、証跡整理を支援する。

成果:

- 調査時間短縮
- レビュー漏れ削減
- 証跡保存
- ナレッジ蓄積

## 10. MVP

### Phase 1: イベントログと抽出

- チャットログ保存
- アップロード資料保存
- 会話から entity / relation を抽出
- 信頼度ラベルを付与
- source citation を保存

### Phase 2: Staging Knowledge Graph

- 抽出結果を staging graph に保存
- confidence に応じて自動昇格またはレビューへ分岐
- 重複検出
- 矛盾検出
- テナント分離

### Phase 3: 回答時の KG 参照

- ユーザー質問から関連サブグラフを取得
- 回答に根拠を付与
- 回答後のフィードバックを保存
- Q&A 結果を再抽出対象に戻す

### Phase 4: インサイト UI

- 中心ノード
- 隠れた関係
- 曖昧な関係
- 推奨質問

### Phase 5: 業務アクション

## 11. 主要リスク

### 11.1 推測が事実として保存される

対策:

- 信頼度ラベル必須
- source span 必須
- 推論と事実を UI 上で区別
- 重要情報は human approval 必須

### 11.2 古い情報が残る

対策:

- valid_from / valid_to
- 失効処理
- 矛盾エッジ
- temporal graph

### 11.3 顧客間データ混入

対策:

- tenant_id 必須
- query layer での境界強制
- tenant-scoped extraction
- cross-tenant 学習は匿名統計のみ

### 11.4 グラフがノイズで膨張する

対策:

- staging graph
- low-confidence edge の自動昇格禁止
- merge policy
- 使用頻度による優先度管理
- 定期レビュー

### 11.5 成果課金の定義が曖昧になる

対策:

- 成果定義を契約に明記
- 成果判定ログを保存
- 顧客側で監査可能にする
- 上限額を設定
- 例外条件を事前に定義

## 12. 競争優位

本プロダクトの優位性は、単一の AI モデルやチャット UI ではなく、以下の組み合わせにある。

- 顧客ごとに育つ private knowledge graph
- 回答だけでなく、業務 DB も自動生成される
- 根拠、信頼度、曖昧さを扱える
- 既存システムへの実行が可能
- シミュレーションと回帰テストがある
- 業務成果と改善ループが接続されている
- 顧客固有の業務メモリが長期的な資産になる

## 13. 最終的な事業像

最終的には、企業のあらゆる業務イベントが AI によって構造化され、知識グラフとして蓄積され、その上で AI エージェントが回答、判断補助、実行、改善を行う状態を目指す。

価値の中心は、AI が賢いことではなく、**企業の業務そのものが、利用されるたびに構造化され、再利用可能になり、改善されること**である。
