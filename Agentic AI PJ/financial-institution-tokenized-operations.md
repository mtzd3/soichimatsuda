# 金融機関向け預金トークン業務基盤構想

作成日: 2026-05-03

## 1. 位置づけ

本構想は、業務知識グラフ型 AI オペレーション基盤を、金融機関の預金、送金、為替、決済、バックオフィス業務に転用するための整理である。

目的は、既存の銀行勘定系、為替システム、AML/CFT、会計、監査、顧客管理を壊さずに、預金や資金移動をプログラマブルな実行レイヤーに接続することにある。

一言で表すと、**預金トークン、為替、送金、承認、照合、監査を統合する金融業務基盤**である。

## 2. 基本方針

金融機関向けに構築する場合、重要なのは「分散台帳で何でも置き換える」ことではない。

現実的な方針は以下である。

- 勘定系は正本として維持する
- トークンは実行、移転、同期、証跡のレイヤーとして使う
- 金銭移動は決定論的なワークフローで制御する
- AI は判断補助、証跡整理、例外検知、承認ルーティングに使う
- 高リスク取引は人間承認を必須にする
- AML/CFT、制裁、権限、限度額、監査を設計の中心に置く
- 複数システム間の照合と例外処理を最初の価値にする

## 3. コアプロダクトとの違い

コアプロダクトは、企業一般の業務知識、会話、文書、システムイベントを構造化し、AI エージェントの回答と業務実行を改善する基盤である。

金融機関向けシステムでは、これに以下が追加される。

- 預金残高との厳密な同期
- mint / burn の統制
- 決済ファイナリティ
- 送金指図
- 為替予約、為替取引、ヘッジ方針
- AML/CFT
- 制裁スクリーニング
- 取引モニタリング
- 本人確認、実質的支配者確認
- 勘定系、総勘定元帳、会計システム連携
- 不正送金対策
- 鍵管理
- 障害時復旧
- 当局、監査法人、内部監査向け証跡

## 4. 対象ユースケース

### 4.1 法人向け国内送金

法人顧客が請求書、契約、発注情報に基づいて支払いを行う。

従来は、支払指図、承認、振込、消込、会計処理、証跡保存が別々に行われる。

本システムでは、以下を統合する。

- 請求書情報の抽出
- 支払先確認
- 権限確認
- 取引目的の確認
- 預金残高確認
- 預金トークン mint
- トークン移転
- burn
- 勘定系反映
- 会計仕訳
- 入出金消込
- 監査ログ保存

### 4.2 クロスボーダー送金

法人が海外取引先へ支払うケース。

必要な処理:

- 送金目的確認
- 受取人確認
- 制裁スクリーニング
- AML/CFT チェック
- 為替レート提示
- 手数料提示
- 着金予定提示
- 為替予約または spot 取引
- 支払指図
- 送金ステータス追跡
- エラー時の例外処理

トークン化は、資金移動の状態を共有し、支払と為替を原子的に近い形で同期するために使う。

### 4.3 為替ヘッジ統合

法人顧客が外貨建て支払い、外貨建て売掛、輸出入取引を持つ場合、支払いとヘッジを分離すると手戻りやリスクが発生する。

本システムでは、以下を統合する。

- 請求書、契約、発注書から外貨エクスポージャーを抽出
- 顧客別ヘッジ方針を参照
- 既存の為替予約残高を確認
- spot / forward / swap の候補を提示
- 与信、限度額、適合性を確認
- 承認後に取引を実行
- 支払指図とヘッジを紐付け
- 会計、時価評価、証跡を保存

### 4.4 証券、債券、担保との DVP

資金と資産の引渡しを同時に行う。

対象:

- デジタル証券
- 債券
- ファンド持分
- 担保
- レポ取引
- 社内資金移動

狙い:

- 決済リスク削減
- 事務負担削減
- 照合負荷削減
- リアルタイム化
- 取引証跡の一元化

### 4.5 バックオフィス自動化

最初に商用価値を出しやすい領域は、派手な送金そのものよりバックオフィスである。

対象:

- 入金消込
- 送金照合
- 為替予約と支払指図の突合
- 例外処理
- AML 調査メモ作成
- 制裁ヒット時の一次調査
- 監査資料作成
- GL 仕訳
- 顧客別取引履歴整理
- 月次レポート

AI と知識グラフは、これらの作業で強い価値を持つ。

## 5. 預金トークンの考え方

### 5.1 預金トークンとは

預金トークンは、銀行預金と紐付いたデジタル表現である。

顧客が銀行に持つ預金債権を、許可型台帳上で移転、ロック、条件付き実行できるようにする。

重要なのは、トークンが独立した無記名資産として自由流通する設計ではなく、銀行の勘定、顧客確認、権限、規制、監査と一体で管理されることである。

### 5.2 stablecoin との違い

金融機関向けの初期設計では、預金トークンと stablecoin を混同しない方がよい。

預金トークン:

- 銀行預金と紐付く
- 銀行勘定と同期する
- 顧客と銀行の関係を維持する
- 銀行内または参加者限定ネットワークで扱いやすい

stablecoin:

- 法定通貨価値に連動する支払手段として発行される
- 発行者、仲介者、移転、償還、利用者保護の規制整理が重要
- より広い流通を想定しやすい

最初の商用化は、預金トークン型の方が銀行業務と接続しやすい。

### 5.3 mint / burn

基本フロー:

```text
預金口座から引当
  -> 指定口座または内部管理勘定へ振替
  -> 預金トークン mint
  -> トークン移転
  -> 受取側で burn
  -> 預金口座へ反映
```

必須要件:

- mint 前の残高確認
- 二重発行防止
- burn 前の保有確認
- 勘定系との整合性
- 失敗時の補償処理
- 操作ログ
- 権限分離
- 監査証跡

## 7. AI の役割

### 7.1 AI が行うべきこと

- 請求書、契約、送金依頼から情報を抽出する
- 必要な承認者を特定する
- 過去の類似取引を探す
- 顧客別のヘッジ方針を要約する
- AML 調査の一次メモを作る
- 制裁ヒットの候補理由を整理する
- 例外処理の原因を推定する
- オペレーター向けの対応案を作る
- 監査向け証跡をまとめる
- 不足情報を質問として提示する

### 7.2 AI が単独で行うべきではないこと

- 高リスク送金の最終承認
- 為替デリバティブの無承認実行
- 顧客資金の不可逆移転
- 制裁ヒットの最終解除
- 顧客属性の無根拠な確定
- 法的判断の最終決定
- 不正疑義の自動クローズ

### 7.3 AI と決定論的ワークフローの分担

AI:

- 読む
- 要約する
- 抽出する
- 候補を出す
- 根拠を整理する
- 例外を分類する

決定論的ワークフロー:

- 残高確認
- 限度額確認
- 権限確認
- 署名
- mint
- transfer
- burn
- 勘定更新
- 監査ログ保存
- 承認状態管理

## 8. システム構成

```text
法人顧客 / 銀行担当者
  -> チャネル
  -> 取引受付
  -> Event Log
  -> 情報抽出
  -> Staging Financial Graph
  -> リスク / 権限 / 根拠チェック
  -> Committed Financial Graph
  -> Workflow Engine
  -> Core Banking Adapter
  -> Token Ledger
  -> FX / Hedge Engine
  -> Compliance Engine
  -> Accounting / GL
  -> Reconciliation
  -> Monitoring / Audit
```

## 9. 代表フロー

### 9.1 法人外貨支払い

```text
請求書アップロード
  -> 通貨、金額、期日、受取人、契約を抽出
  -> 顧客の承認ルールを確認
  -> AML / 制裁チェック
  -> 外貨エクスポージャーを作成
  -> 為替 quote を提示
  -> hedge 必要性を判定
  -> 顧客承認
  -> 預金引当
  -> 預金トークン mint
  -> FX 実行
  -> 送金実行
  -> token burn
  -> 勘定更新
  -> 消込
  -> 監査ログ保存
```

### 9.2 国内 DVP 決済

```text
資産売買約定
  -> 売り手資産を一時ロック
  -> 買い手預金を引当
  -> 預金トークン mint
  -> 支払情報を同期
  -> 資産移転と資金移転を同時実行
  -> 預金トークン burn
  -> 勘定更新
  -> 照合
  -> 例外確認
```

### 9.3 AML 例外対応

```text
取引モニタリングで alert
  -> 顧客、受益者、過去取引、契約、請求書を graph で取得
  -> 類似ケースを検索
  -> alert 理由を要約
  -> 不足情報を特定
  -> 担当者に調査メモを提示
  -> 担当者が承認 / 差戻し / エスカレーション
  -> 判断根拠を graph に保存
```

## 10. 導入ロードマップ

### Phase 1: Back Office Copilot

最初は資金移動を行わず、既存データを読み、照合、証跡整理、例外分類を行う。

機能:

- 請求書、契約、送金依頼の抽出
- 入出金消込支援
- AML 調査メモ
- 為替予約と支払指図の突合
- 監査資料作成

目的:

- データ接続を確認する
- 業務知識グラフを育てる
- 現場の信頼を得る
- 規制リスクを抑える

### Phase 2: Tokenized Deposit Sandbox

限定された社内環境で、預金トークンの mint / transfer / burn を検証する。

対象:

- 社内口座
- テスト顧客
- 限定金額
- 単一通貨
- 手動承認

目的:

- 勘定系同期
- 二重発行防止
- 障害時復旧
- 監査ログ
- 会計処理

### Phase 3: 法人国内決済

限定法人顧客に対して国内決済を提供する。

対象:

- 請求書支払い
- グループ内資金移動
- 仕入先支払い
- 消込自動化

目的:

- 実業務での効率化
- 顧客 UX 検証
- 例外処理の蓄積

### Phase 4: FX / Hedge Integration

外貨建て支払いと為替ヘッジを統合する。

対象:

- spot
- forward
- swap
- 支払指図との紐付け
- ヘッジ方針管理
- 限度額管理

目的:

- 外貨支払いの一気通貫化
- ヘッジ漏れ削減
- 証跡の標準化

### Phase 5: Interbank / Cross-border

複数金融機関、複数通貨、海外送金へ拡張する。

対象:

- 限定コリドー
- 参加銀行限定
- 企業顧客限定
- 明確なルールブック

目的:

- 24/7 に近い資金移動
- 透明な手数料
- 送金状態の可視化
- PvP 的な settlement risk 削減

## 12. 主要リスク

### 12.1 法的位置づけ

預金トークン、電子的支払手段、前払式支払手段、暗号資産、電子記録移転権利などの区分を誤ると、必要な登録、業規制、顧客保護、会計処理が変わる。

対策:

- 初期段階から法務、コンプライアンス、当局対応を組み込む
- まず銀行内または限定参加者ネットワークで始める
- 顧客資金の権利関係を明確化する

### 12.2 勘定系との不整合

トークン台帳と勘定系がズレると重大事故になる。

対策:

- 勘定系を正本とする
- mint / burn は必ず勘定イベントと紐付ける
- reconciliation をリアルタイムまたは準リアルタイムで行う
- 不一致時は自動停止する

### 12.3 不正送金

トークン移転は即時性が高いため、不正時の被害が大きい。

対策:

- 多要素認証
- HSM
- 署名権限分離
- 金額別承認
- 異常検知
- 取引保留
- 緊急停止

### 12.4 AML/CFT

高速化により、疑わしい取引の検知と停止が遅れるリスクがある。

対策:

- 取引前スクリーニング
- 取引中モニタリング
- 取引後レビュー
- 受益者情報保持
- ルールとモデルの併用
- 調査証跡の保存

### 12.5 AI の誤判断

AI が誤って低リスクと分類したり、不適切なヘッジ提案をする可能性がある。

対策:

- AI は推薦と整理に限定する
- 高リスク判断は人間承認
- すべての提案に根拠を持たせる
- モデル出力を監査対象にする
- シミュレーションと回帰テストを行う

## 13. 成功条件

このシステムの成功条件は、トークン化そのものではない。

成功条件は以下である。

- 既存業務より照合が楽になる
- 既存業務より証跡が明確になる
- 既存業務より例外処理が速い
- 既存業務より資金状態が見える
- 既存業務より顧客説明がしやすい
- 既存業務より監査に耐えやすい
- 既存業務より為替と支払いの接続が自然になる

## 14. 最終像

最終的には、金融機関の預金、為替、送金、証券決済、担保、会計、AML、監査が、共通のイベントログと知識グラフで接続される。

AI は金融取引を勝手に実行するのではなく、取引の文脈、根拠、リスク、承認、例外を整理する。

価値移動は決定論的に、判断は監督付きで、証跡は構造化され、業務改善は継続的に行われる。
