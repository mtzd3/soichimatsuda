## 0. 結論

日本が守るべきものは、単なる「国産モデル」でも「国内保存されたデータ」でもない。

守るべきものは、金融、製造・エネルギー、宇宙、ロボティクス、交通・物流、防衛・公共インフラにおいて、

1. 何を観測し、
2. どのデータを利用し、
3. どのモデルで判断し、
4. どの更新を採用し、
5. 誰の権限で実行し、
6. どの状態を変更し、
7. どのように監査・停止・復旧するか

を国内主体が継続的に決定できる能力である。

これを本書では、**主権的な学習・実行ループ**と呼ぶ。

KairosAIの戦略は、汎用巨大モデルを最初から後追いすることではない。重点領域の現場にAIと統治基盤を実装し、そこから生じる高価値な判断・実行・結果データを、権利処理、評価、配備、監視、rollbackまで含む国内ループへ接続する。その運用実績が十分に蓄積した段階で、共有コア、効率特化HW、大規模計算基盤へ進む。

戦略を支える三本柱は次のとおりである。

| 柱 | 正準名称 | 提供価値 | 主権上の焦点 |
| --- | --- | --- | --- |
| **柱A** | モデル・データ | 重点領域のAgentic AI、領域専門家、共有コア、学習・評価・更新ループ | 学習権、運用権、更新権 |
| **柱B** | 計算基盤 | オンプレ計算、共通ソフトウェアスタック、電力効率、条件付き専用HW | 計算継続能力、効率、供給耐性 |
| **柱C** | 実行基盤 | state registry、policy、provenance、承認、実行、settlement | 状態更新権、実行権、決済権、捕捉権 |

三本柱は同時に立ち上げる。ただし現場では、柱Aと柱Cを一体導入し、柱Bがその稼働を支える。

> **現場ではAとCが高価値データを共同生産し、Bがそれを外へ出さずに動かす。**

## 1. なぜ今、主権の定義を更新する必要があるのか

### 1-1. 問題はサービス利用ではなく、判断基盤の外部固定化である

クラウド、OS、検索、広告、アプリ流通、生成AI APIなど、デジタル活動の主要レイヤーは外資基盤への依存が大きい。既存ITを短期間ですべて置き換えることは現実的ではない。

しかし、これからAIが入り込む産業・社会・行政の判断基盤は、まだ設計を選べる余地がある。

ここで外部依存を固定すれば、失うのは利用料だけではない。

- どのデータを収集するか
- 専門家の訂正をどこへ蓄積するか
- 何をモデルの重みに入れるか
- どのmodel versionを採用するか
- 誰が配備を承認するか
- 問題時にどこへ戻すか
- 誰が現実の状態を更新するか

という判断のOSそのものが外部に固定される。

### 1-2. AI Agentと永続記憶が、保護対象を拡張する

会話型AIの主な出力は文章である。一方、AI Agentはイベント、権限、残高、在庫、契約、設備状態を継続的に読み、ツールを呼び出し、状態を更新する。

さらに永続記憶型のエージェントは、個別の会話だけでなく、次の情報を時間とともに蓄積する。

- 利用者の判断傾向
- 組織の暗黙知
- 業務手順と例外処理
- Tool Useの履歴
- 訂正、承認、却下のパターン
- 成功・失敗と業務outcomeの対応

したがって保護対象は、個人情報、営業秘密、国家機密というコンテンツ単位だけでは足りない。**判断ループ、更新履歴、業務適応手順、実行テレメトリ**も主権資産として扱う必要がある。

### 1-3. 主権は八つの権利として定義する

KairosAIにおける主権は、少なくとも次の八つで構成する。

1. **保存権**: 原本と機微情報の保管場所を選べる
2. **利用権**: 何の目的でデータを利用できるかを決められる
3. **学習権**: どのデータをどの学習へ投入するかを決められる
4. **運用権**: モデル、鍵、runtimeを国内主体が運用できる
5. **更新権**: model version、adapter、評価基準を更新できる
6. **配備・取消権**: 署名、canary、停止、rollbackを実行できる
7. **実行・決済権**: 現実の状態変更と精算を国内レールで完遂できる
8. **監査権**: データ、モデル、判断、実行の来歴を追跡できる

国内にサーバーがあるだけでは、この八つは成立しない。

## 2. 戦略対象

### 2-1. 重点六領域

| 領域 | 主な対象 |
| --- | --- |
| 金融・決済・資金移動 | 与信、決済、資金移動、ヘッジ、規制対応 |
| 製造・エネルギー・産業運営 | 需給、生産、保全、調達、在庫、制御 |
| 宇宙データ | 観測、航法、軌道、衛星運用 |
| ロボティクス・自律機械 | 産業ロボット、物流ロボット、ドローン、自動運転、建機 |
| 交通・物流・モビリティ | 配送、フリート、交通流、地図、運行 |
| 防衛・安全保障・公共インフラ | 指揮支援、演習、兵站、サイバー防衛、設備監視 |

六領域は固定的な縦割りではない。製造と金融、ロボティクスと物流、宇宙と防衛のように、実務では相互に接続する。

初期に全領域へ同時展開するのではなく、次の基準で2〜3領域を選ぶ。

- 主権上の重要度
- 現場導入先と責任者の明確さ
- outcomeを測定できること
- 権利処理可能なデータが継続発生すること
- 他領域へ再利用できる評価・ソフトウェア資産が得られること
- 誤実行時の安全境界を設計できること

### 2-2. 守る対象はデータではなく、判断・実行・更新の連鎖である

各領域に共通する構造は次のとおりである。

```text
現場の状態・イベント
  ↓
権利とポリシーの判定
  ↓
モデルによる判断
  ↓
人間または機械による承認
  ↓
業務システム・機械・決済系への実行
  ↓
結果・失敗・例外・outcomeの記録
  ↓
評価、学習、更新
  ↓
署名、再配備、監視、rollback
```

この連鎖の一部だけを国内化しても、主権は完成しない。

## 3. 三本柱の正準定義

### 3-1. 柱A — モデル・データ

柱Aは、重点領域のAI能力と継続更新能力を担う。

初期は高品質なOSSモデルを出発点としてよい。重要なのは初期重みの国籍ではなく、次を国内に蓄積することである。

- 共通の祖先checkpointとtokenizer
- 領域専門家と拠点adapter
- RAG、KG、Tool API
- 評価ハーネスと失敗分類
- データ権利とprovenance
- release package
- 配備・監視・rollback手順
- 業務outcomeと判断ログ

目標構成は、単一の万能モデルではなく次の三層である。

1. **共有コア**: 日本語、制度理解、横断推論、計画、Tool Use
2. **領域専門家**: 金融、製造、宇宙、防衛等の専門判断
3. **拠点ローカル層**: 企業・施設固有の手順、分類情報、例外

### 3-2. 柱B — 計算基盤

柱Bは、重要データを管理境界の外へ出さずにAIを稼働させる能力を担う。

柱Bには二つの異なる計算スコープがある。

| スコープ | 目的 | 規模の考え方 |
| --- | --- | --- |
| **Site Compute** | 顧客・施設内の推論、RAG、評価、軽量学習 | 1〜数十GPUをProfile別に増設 |
| **Shared Sovereign Compute** | 複数領域の統合検証、共有コアの重い更新、大規模学習 | 国家・共同基盤として別途整備 |

両者を混同しない。顧客オンプレに数百〜数千GPUを置くことを標準構成とはしない。

柱Bの初期目標は、GPUの台数ではなく、次の共通ソフトウェア契約を確立することである。

- framework互換
- model interchange
- compiler / runtime
- model・data registry
- evaluation / release control
- model / compute routing
- 監視、署名、canary、rollback

専用HWは必達目標ではない。実装テレメトリが必要性を証明した場合だけ進む。

### 3-3. 柱C — 実行基盤

柱Cは、AIの判断を安全な状態変更へ変換し、その履歴を残す。

中核コンポーネントは次の四つである。

| コンポーネント | 役割 |
| --- | --- |
| **state registry** | 状態、権利、対象、model version、承認状態を機械可読に保持 |
| **policy engine** | 誰が、何を、どの条件で実行できるかを判定 |
| **provenance ledger** | データ、モデル、判断、実行、結果の来歴を追跡 |
| **settlement / action rail** | 承認済みactionを業務・制御・決済系へ接続 |

「tokenization」は必ずしもブロックチェーンやデータ本体のトークン化を意味しない。本書では、**権利、状態、利用条件、履歴、精算条件を機械可読なregistryとして表現すること**を基本とする。

### 3-4. 三柱の関係

三柱は「順番に完成させる工程」ではなく、並行するワークストリームである。

```text
柱A: Agentが判断・outcome・失敗を生む
  ↕
柱C: 状態・権利・承認・実行・履歴を捕捉する
  ↕
柱B: 企業・施設内で安全かつ効率的に動かす
```

説明順はA→B→Cに統一する。ただし因果関係を単純な一方向と解釈しない。

- AとCが現場で高価値データを共同生産する
- BがAとCをオンプレで稼働可能にする
- A/CのテレメトリがBの将来HW要件を定義する
- Bの効率向上がA/Cの導入コストを下げる

## 4. 知識配置とデータ主権

### 4-1. すべてをモデルの重みに入れない

| 情報の性質 | 原則的な配置 |
| --- | --- |
| 最新の規程、残高、在庫、契約、設備状態 | RAG、KG、state registry、API |
| 企業固有手順、顧客固有情報、分類情報 | 拠点ローカルadapter、閉域RAG |
| 反復可能な専門判断、成功・失敗パターン | 領域専門家、報酬モデル、評価セット |
| 複数領域で再利用可能な推論・計画・Tool Use | 共有コアの更新候補 |
| 削除要求が想定される個人情報・秘密情報 | 原則として重みに入れない |

データ主権とは、何でも国内モデルへ学習させることではない。**何をどこに置き、いつ更新し、どう削除し、どのmodel versionへ影響したかを説明できること**である。

### 4-2. 資産は二種類に分ける

「Layer 1」という語は既存文書で複数の意味に使われているため、資産分類には使わない。

| 資産区分 | 内容 | 原則 |
| --- | --- | --- |
| **顧客主権資産** | 原本データ、企業固有知識、分類情報、残高・在庫等の状態、秘密手順 | 顧客境界内に残す。共有しない |
| **共有可能学習資産** | 権利処理済みテレメトリ、評価レシピ、失敗分類、匿名化・集約例、報酬モデル、adapter差分 | 契約、registry、評価を通じて限定再利用 |

共有可否は「匿名化したから可」ではなく、目的、権利、再識別可能性、越境、保持期間、取消可能性を含めて判定する。

### 4-3. 学習・更新パイプライン

```text
現場導入
  ↓
判断・実行・結果・例外の記録
  ↓
権利判定、原本保全、分類、PII処理
  ↓
知識配置判定
  ├─ 外部記憶・state
  ├─ 拠点ローカル層
  ├─ 領域専門家
  └─ 共有コア候補
  ↓
品質管理、データ混合、学習
  ↓
領域性能・安全性・privacy・outcome・効率評価
  ↓
署名、canary、配備
  ↓
監視、停止、rollback
```

配備単位は重みだけではなく、次を束ねたrelease packageとする。

- model / adapter version
- 利用条件
- データ系譜
- 評価結果
- 実行ポリシー
- rollback target
- 署名と有効期限

## 5. オンプレ実行の正準境界

### 5-1. 基幹系を置き換えない

KairosAIオンプレは、顧客のERP、コアバンキング、制御系、既存台帳を一括置換しない。

| 対象 | 正準方針 |
| --- | --- |
| 基幹系の取引・業務状態 | 顧客システムをsource of truthとして維持 |
| KairosAIからの参照 | 公式API、CDC、承認済みadapterを使用 |
| 直接DB write | 原則禁止 |
| 書き戻し | Policy Gateと必要なHuman Reviewを通す |
| 派生知識 | Graph、vector、event storeで保持可能 |
| 原本 | 顧客管理境界内に保持。GraphにはURI、hash、source span等を記録 |

証跡用ファイルや承認済みスナップショットをKairosAI側Object Storeへ取り込む場合も、保存主体、正本性、保持期限を明示する。Graphやregistryを原本と混同しない。

### 5-2. 物理ゾーン

| Zone | 主な構成 |
| --- | --- |
| GPU Zone | 推論、model cache、必要に応じた軽量学習 |
| App Zone | agent runtime、policy engine、workflow、Human Review |
| Data Zone | event store、state registry、vector、graph、provenance |
| Integration Zone | 基幹系read adapter、承認付きwrite-back adapter |

最低要件は次のとおりである。

- zone分離と最小権限
- 暗号化と鍵の顧客管理
- 外部egressの原則deny
- model callとpolicy decisionの紐付け
- tamper-evidentな監査ログ
- offline import / export
- air-gap対応Profile

### 5-3. Site Compute Profile

| Profile | 想定用途 | 参考GPU規模 | 実行範囲 |
| --- | --- | --- | --- |
| Lab | 社内検証 | 1 | 推論・評価 |
| Pilot | 顧客pilot | 1〜2 | 提案中心、重み更新なし |
| Production | 部門本番 | 4〜8 | 推論、RAG、夜間LoRA/DPO |
| Regulated | 規制産業本番 | 8〜16 | 専用DB、厳格provenance |
| Enterprise | 全社・複数部門 | 32以上 | 複数ノード、専用learning plane |

GPU種類、VRAM、network、冷却方式は、モデルサイズではなく実測のlatency、throughput、同時実行数、KV cache、可用性要件から決める。

## 6. 計算・電力・半導体戦略

### 6-1. 電力は二つのスコープで解く

既存文書の「電力は調達ではなく効率で解く」と「電力主権として長期確保する」は、対象スコープが異なる。

正準方針は次の一文に統合する。

> **顧客オンプレでは効率で解き、国家・共同計算基盤では量・立地・電源構成を長期確保する。**

| スコープ | 主課題 | 基本戦略 |
| --- | --- | --- |
| Site Compute | 既存ラック、電力、冷却、騒音、調達制約 | business outcome per joule、量子化、routing、効率HW |
| Shared Sovereign Compute | 大規模更新、共同学習、国家基盤 | 長期電力契約、立地分散、系統接続、電源構成、災害耐性 |

また、柱Cが管理する「電力融通枠・充電枠等の業務状態」と、柱Bを動かす「計算用電力」は別の概念として扱う。

### 6-2. GPU先行の意味

GPU先行の目的は、GPU依存を永久化することではない。

先にGPU上で、

- API
- SDK
- model format
- compiler path
- runtime
- evaluation
- release
- monitoring

の運用契約を成立させる。その実運用テレメトリを将来HWの仕様へ変換する。

### 6-3. 専用HWのgo/no-go

専用HWへ進む条件は、少なくとも次の三つとする。

1. 特定演算が顧客TCOまたは電力の支配要因である
2. 電力・冷却制約により導入・拡張を断念した事例が複数ある
3. ソフトウェア互換、設計人材、製造、資金の実行体制がある

条件を満たさない場合は、既存アクセラレータ、カスタムカーネル、FPGA、量子化、routingで対応する。

### 6-4. 技術標準を目的化しない

CXL、ONNX、MLIR、LLVM、Triton等は有力な実装候補であるが、特定バージョンを戦略正本の必達条件にはしない。

採用標準は、各PhaseのArchitecture Gateで次を評価して決める。

- 製品成熟度
- 相互運用性
- 性能と電力
- セキュリティ
- 国内運用可能性
- ベンダーロックイン
- 移行コスト

## 7. 実装・事業化メカニズム

### 7-1. 需要形成を先に置く

初期の優先順位は、組織形態や大型資金スキームを固定することではない。

先に確保すべきものは、

- 現場課題
- 導入責任者
- 実証フィールド
- outcome KPI
- データ発生源
- 権利処理
- 本番移行条件

である。

PoC件数ではなく、本番運用、更新サイクル、再利用資産、主権KPIを評価する。

### 7-2. プログラム運営

全体には次の機能を置く。

| 機能 | 主な責任 |
| --- | --- |
| Program Authority | 戦略、投資配分、領域優先順位、停止判断 |
| Model Steward | 共有コア、領域専門家、version、互換性 |
| Data / Rights Steward | 権利、越境、保持、削除、共有条件 |
| Evaluation Authority | 独立評価、安全性、配備判定 |
| Compute Operator | Site / Shared Compute、再現性、TCO、電力 |
| Deployment / Incident Authority | 署名、配備、停止、rollback |
| Domain Council | 現場基準、許容リスク、評価更新 |

開発者が自ら最終配備を承認する構造は避ける。

### 7-3. SPC、公共層、営利層の位置づけ

SPC、一般社団法人、営利会社、ファンド、BOTは、案件形成や資金調達の候補であり、戦略の必須構成ではない。

採用する場合は、案件ごとに次を満たす必要がある。

- IPとデータ権利が明確
- 顧客主権資産を共有資産へ移さない
- 評価機能と販売機能の利益相反を管理
- 公的資金と民間収益の会計を分離
- 非差別アクセスの対象と条件を明文化
- 終了・売却後もデータ利用条件が維持される

共有コアを公共的に運営することは有力な選択肢だが、特定法人による恒久保有を本書では確定しない。中立性、透明性、継続運用、セキュリティ、国際連携を比較して決定する。

## 8. 実行ロードマップ

Phaseは三本柱ではなく時間軸である。各柱は全Phaseを通じて成熟する。

期間は、正式なプログラム開始日をT0として数える。固定された暦年と混同しない。

### Phase 1 — 現場ループの成立（T0〜18か月）

**目的**: 2〜3領域で、判断・実行・評価・更新の閉ループを本番相当で成立させる。

- 柱A: OSS基盤、領域RAG、adapter、評価ハーネス
- 柱B: Site Compute Profileの確立、GPU共通スタック
- 柱C: registry、policy、provenance、承認付きactionの最小実装
- 権利: 学習可否、保持、越境、削除、再利用条件のschema化
- 調達: モデル改善目的の保持・再利用、監査、停止、移行に関する標準条項
- KPI: 本番継続率、評価通過率、rollback時間、権利追跡率、業務outcome

Phase 1では、巨大モデルの自前学習を成功条件にしない。

### Phase 2 — 複数領域・複数拠点への拡張（18〜36か月）

**目的**: 現場ループを複数組織へ展開し、共通資産と固有資産の分離を実証する。

- 共通祖先から領域専門家を並列育成
- 複数拠点の権利・評価・release形式を統一
- Site ComputeをProfileに応じて拡張
- Shared Sovereign Computeの必要量、立地、電力、運営主体を確定
- 実行テレメトリから効率HWのgo/no-goを判定
- settlementは限定領域・上限付きで段階導入

### Phase 3 — 共有コアと国家・共同基盤への接続（36〜60か月）

**目的**: 権利処理済み資産を使い、共有コアの重い更新を国内主導で回す。

- 継続事前学習とreplay
- 領域専門家のroutingまたは条件付きMoE化
- Shared Sovereign Computeの運用
- 独立Evaluation Authorityによる横断ゲート
- 条件成立時のみ専用HWの試作・初回シリコン
- 規制産業でのprovenance、incident response、rollback標準化

### Phase 4 — 選択的な大規模化・量産（60か月以降）

**目的**: 実績とゲートを満たす場合だけ、国産共有コアの大規模学習と効率HW量産へ進む。

実行条件は次のとおりである。

- 横断能力の改善が再現される
- 権利処理と取消可能性が成立する
- 他領域と安全性を劣化させない
- 計算・電力・運用コストを便益が上回る
- 国内主体が継続運用できる

単一巨大モデルへ統合しない判断も正当な最終形とする。

### 政策上の三つの時間帯

既存文書の「2026〜28 / 2027〜30 / 2030〜35」は、上記Phaseとは別の政策時間帯として扱う。

| 政策時間帯 | 主題 |
| --- | --- |
| 近接期 | 現場実装、調達条項、rights schema、Site Compute |
| 中期 | 複数領域展開、Shared Compute計画、電力・立地、HW判定 |
| 長期 | 共有コア主権化、条件付きASIC、大規模運用 |

## 9. 政府への統合提言

### 9-1. 基本姿勢

政府の役割は「国産モデルを一つ作ること」ではない。

次の四つを整えることである。

1. **資金**: 現場実装、共通基盤、評価、計算基盤への段階投資
2. **規制**: 学習、保持、越境、実行、監査、取消の要件
3. **調達**: 移行可能性、監査可能性、国内継続性を契約条件化
4. **国家プログラム連携**: 既存計算基盤、研究、人材、半導体、電力政策の接続

### 9-2. 柱Aへの提言

- 重点領域の領域専門家、評価ハーネス、更新ループを支援する
- データの学習権、再利用、越境、保持、削除を機械可読にする
- モデル改善目的のデータ利用条件を重要セクター調達で明示する
- 訂正、承認、却下、Tool Use、永続記憶を保護対象として評価する
- モデルサイズではなく更新時間、評価通過率、外部依存率をKPIにする

### 9-3. 柱Bへの提言

- Site ComputeとShared Sovereign Computeを別政策として設計する
- GPU共通スタックとmodel lifecycle基盤を優先する
- Shared Computeでは長期電力、立地分散、系統接続、災害耐性を早期に確保する
- 専用HW支援はgo/no-go連動型とする
- 製造拠点を単一前提にせず、設計IP、試作、量産、packagingの代替経路を持つ

### 9-4. 柱Cへの提言

- registry、policy、provenance、approval、settlementの相互運用標準を整備する
- AIが状態変更する場合の承認階層、上限、監査、緊急停止を要件化する
- 国内保存だけでなく、実行権、決済権、rollback権の国内保持を評価する
- 行政を主権的Agent運用のリファレンス実装にする

### 9-5. 電力への提言

- Site Computeには効率基準を設ける
- Shared Computeには長期電源計画を設ける
- AI計算を電源投資の長期需要家として活用する可能性を評価する
- 立地、電源構成、カーボン強度、災害耐性を一体で比較する
- 個別電源や地域を戦略正本で固定せず、更新可能な計画として管理する

## 10. 評価指標

### 10-1. 主権KPI

- 外部API停止時にも継続できる重点業務の比率
- model versionからデータ、権利、評価、配備先を追跡できる比率
- 機械可読な利用条件が付与された学習資産の比率
- 問題発生から停止・rollbackまでの時間
- 国内主体が鍵、runtime、配備を管理する比率
- 顧客主権資産が境界外へ出ない比率

### 10-2. 業務KPI

- 処理時間、停止時間、損失、回収率、精度等の業務outcome
- 人間の例外処理負荷
- 誤実行とnear miss
- 本番継続率
- 現場知見を安全な更新へ反映するまでの時間

### 10-3. 技術・経済KPI

- latency、throughput、availability
- evaluation pass rate
- deployment frequency
- TCO
- business outcome per joule
- GPU・アクセラレータ利用率
- ベンダー移行に要する時間と費用

パラメータ数、GPU台数、PoC件数を単独の成功KPIにしない。

## 11. 主要リスクとゲート

| リスク | 対応 |
| --- | --- |
| OSSまたは外部モデルへの固定化 | 共通祖先、評価、registry、model interchangeを国内管理 |
| 現場データの過剰共有 | 顧客主権資産と共有可能資産を分離 |
| Agentの誤実行 | policy、承認、上限、sandbox、監査、緊急停止 |
| 共有コアによる機微情報の混入 | knowledge placement、権利ゲート、抽出評価 |
| 開発と評価の利益相反 | 独立Evaluation Authority |
| 巨大計算投資の先行 | Phase 3以降、需要と権利資産の成立をゲート化 |
| 専用HWの技術・市場失敗 | go/no-go、既存アクセラレータ経路を維持 |
| 電力・系統の遅延 | Shared Compute計画と同時に立地・電源を確保 |
| 単一製造拠点への依存 | 複数試作・製造・packaging経路 |
| 人材不足 | 現場、ML、compiler、chip、securityを横断する育成・採用 |
| 法制度の追随遅れ | 契約標準と技術的policy enforcementを先行 |

## 14. 最終メッセージ

KairosAIが作るべきものは、単独のモデルでも、単独のデータセンターでも、単独の半導体でもない。

作るべきものは、

- 現場で価値を生み、
- 重要データを境界内に残し、
- 判断と実行の来歴を追跡し、
- 安全に更新し、
- 問題時に止めて戻し、
- 外部サービスが変わっても国内で継続できる

**主権的な学習・実行システム**である。

汎用モデルは、そのシステムが成熟した先に選べる手段の一つであって、出発点でも唯一の終点でもない。

国家主権の回復とは、モデルを所有することではなく、**日本の重要な判断基盤を、日本側の意思で更新し続けられる状態をつくること**である。
